## 上传与执行

将 `yuhetang-full-update-{{RELEASE_ID}}.tar.gz` 和同名 `.tar.gz.sha256` 上传到服务器 `/home/ubuntu`，逐行执行：

```bash
cd /home/ubuntu
sha256sum --check yuhetang-full-update-{{RELEASE_ID}}.tar.gz.sha256
tar -xzf yuhetang-full-update-{{RELEASE_ID}}.tar.gz
sudo bash /home/ubuntu/yuhetang-full-update-{{RELEASE_ID}}/update.sh
```

预期输出 `SUCCESS: SERVER RELEASE {{RELEASE_ID}}`，镜像 `yuhetang-java-api:{{RELEASE_ID}}`、`Health=healthy`。JAR SHA256：`{{JAVA_SHA256}}`。重复执行会核对运行版本、环境变量、数据库映射和前端；全部一致时不再重启。

默认站点根目录为 `/opt/1panel/www/sites/mp-admin/index`，域名 `mp-admin.hetuonian.cn`。保留当前 1Panel / OpenResty 的域名、证书、反向代理及 `MP_verify_*.txt` 校验文件。旧 `yuwatang-reservation.service` 应保持停用；若它又处于活动或开机启用状态，更新器会在停 Java 前指出端口冲突风险。

更新器先校验全部包文件、构建 Java 镜像，再停止本项目旧 Java，并备份独立 `yuwatang_reservation` 库、上传文件、环境及前端，保存到 `/var/backups/yuhetang-unified/`。旧容器保留。新 Java 启动执行缺失迁移，V11 新增改约申请表，原预约和历史保留。新 Java 健康后发布前端资源，最后原子替换 HTML 入口。

本次不安装或重建 MySQL，不执行初始化数据导入；此前导入的门店、品项、调理师和客户记录继续保留。小程序客户端另行交付：本轮删除旧订阅操作、预约截止及改约展示修改需要上传新的小程序体验版，更新服务器不能替换手机旧版页面。先完成本包，再使用本轮 Taro `dist/weapp` 编译结果上传体验版。服务器上运行与真实微信收件需按下文验收，本地校验不能代替。

## 预约操作和店长详情

客户取消和申请改约均受本店 `cancelHours` 规则约束，默认到店前 2 小时截止；等于截止时刻及到店后均关闭。页面自动收起按钮，Java 同时校验接口，旧页面也不能绕过。规则为 0 时仍不能在到店开始及之后自行操作。

客户提交改约后原时间、名额和状态保持不变。门店在「改约待处理」筛选或消息对应的预约详情中确认/未通过；确认时再次检查新名额，失败不改变原预约。未通过需填写原因，客户撤回及申请超时均保留原预约。详情含原时间、申请时间、人数、期限及处理记录。客户通知按已有一次性模板授权发送，不虚构持续订阅。

店长模板消息 URL 携带预约编号：`https://mp-admin.hetuonian.cn/admin?appointment=YHT-预约编号`。未登录时先登录，随后自动打开该预约详情；其他门店账号仍受权限校验。微信后台「跳转文案 → 管理文案」保留「点击查看详情」。本地验证记录在 `validation/admin-appointment-changes.json`，完整流程见 `docs/预约取消与改约闭环.md`。

## 表单编辑统一修复

以下五处均支持逐条添加、删除及多行粘贴，修改后仍需点击所在页面的保存按钮：

| 入口 | 本次调整 |
| --- | --- |
| 品牌与内容 → 总部养护项目 → 养护步骤 | 编号逐步编辑，＋/− 增删、箭头排序、回车插入下一步 |
| 品牌与内容 → 门店独立品项 → 养护步骤 | 相同操作，保存只修改本店独立品项 |
| 门店与时段 → 门店资料 → 门店相册 | 逐图增删排序、素材库选择、多行路径粘贴 |
| 品牌与内容 → 空间相册 | 同样支持逐图编辑和多图选择 |
| 门店与时段 → 预约规则 → 休店日期 | 逐日选择、＋/− 增删，也可粘贴换行或逗号分隔的日期 |

输入过程中保留空白行、尚未完成的内容及中文输入法确认操作。保存时去除空白行和首尾空格；相册及日期同时去重，养护步骤保留有意重复的内容及排序。无效休店日期会显示具体错误并保留草稿，不发送保存请求。普通品牌故事、首页封面标题和产品介绍继续保留自然段落与换行。

部署并强制刷新后，任选一个品项验证新增、删除、排序与保存回显；再检查另一门店数据仍保持原值。本包附带 `validation/admin-list-editors.json`，记录浏览器中的编辑、权限、门店隔离及 2560/1440/1024/390 宽度检查；这些验证使用隔离测试数据，不写线上数据库。

## 部署后验收

1. 浏览器打开 `https://mp-admin.hetuonian.cn/admin`，按 Ctrl+F5 强制刷新；总部账号应看到「服务号菜单」。
2. 进入「消息中心 → 管理后台消息推送」，点击「检查店长服务号配置」。应显示凭证、正式模板和五字段匹配；此检查不发送消息。
3. 选择测试门店，确认「门店接收人微信提醒」已开启并保存、本店接收人已完成本人绑定且关注此服务号。已有有效绑定不需重复操作。
4. 客户微信创建一笔新的测试预约，**先不要确认预约**。等 10～30 秒，在服务号查看店长通知，同时按新预约编号核对消息中心 SERVICE / 新预约申请记录。微信接口受理和手机收到分别核对。
5. 点击服务号消息「查看详情」，登录后应直接打开同一预约编号。核对五字段并确认接待，随后检查客户收到处理提醒。到店提醒按本店规则运行。
6. 上传本轮小程序编译结果，在手机重新进入新的体验版。「我的预约」不再显示独立订阅卡片。另建超过自助提前小时数的未来预约，测试改约申请、门店确认/未通过、客户撤回和截止状态；按 `docs/预约取消与改约闭环.md` 验收。

历史预约已经确认、取消或状态版本改变时，旧待接单任务会停止。不要通过重发旧阻断记录测试新配置。

## 服务号菜单

更新只提供页面、接口、草稿存储及权限，**不自动发布微信菜单**。

进入「服务号菜单」，首次会预填「在线预约、门店查询、我的预约」。可先点「读取微信菜单」核对或载入此前在微信配置的菜单，再修改、保存草稿。确认预览后点击「发布到微信 → 确认发布」。发布前自动备份微信当前默认菜单；必须收到微信成功响应才显示“微信已接受”。

菜单中的小程序 AppID 和页面路径须对应已关联的正式小程序；重新进入服务号核对入口。具体编辑、权限与恢复方式见 `docs/服务号菜单配置.md`。旧平台若仍同步菜单，需要停止其菜单同步，避免覆盖。

## 失败恢复

镜像准备或配置检查失败时保留旧 Java。停止旧 Java 后若失败，更新器检查数据库结构：结构未改变时恢复此前店长配置和前端入口并重启旧 Java；若迁移已改变结构，则停止新容器的自动重启、保留失败容器和私密启动日志，保留数据库及备份等待定位，不自动将数据库覆盖回旧状态。

遇到 `STOP` 或 `RECOVERY REQUIRED`，保留最后输出中的容器名、备份路径和错误；不要重复运行旧初始化脚本或手动启用旧 systemd Java。

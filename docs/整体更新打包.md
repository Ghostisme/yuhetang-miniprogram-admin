# 三端累计更新包

三个源码仓库继续分别开发和提交：管理后台 `yuhetang-miniprogram-admin`、Java `yuhetang-miniprogram-backend`、Taro `yuhetang-miniprogram`。汇总脚本位于本仓库 `tools/package-unified.py`，只读取另两个仓库的已构建产物。

本次组件基线为 `20261108-142200`。Java JAR 与该版本的 148 项通过记录、管理后台 ZIP 及其校验清单一起复用，小程序使用当前源码提交之后生成的 weapp/H5 正式构建。汇总版本有独立时间戳；Java 镜像以汇总版本标记，`manifest.json` 同时记录组件基线、三个源码提交及每个文件摘要。

打包前提交所有源码变更，准备对应的 Java Docker 组件包和管理后台 ZIP，并完成 Taro 正式构建。汇总脚本会拒绝未提交的仓库、与当前后端提交不一致的 JAR、早于源码的前端产物、组件校验不符和重复使用的发布编号。

在管理后台仓库执行：

```powershell
python -X utf8 -B tools/test_unified_update.py
python -X utf8 -B tools/package-unified.py --component-release 20261108-142200
```

后续有业务代码变化时，先构建并校验新的组件，再把 `--component-release` 换成对应的累计组件版本。仅更新交付脚本或说明时，可以复用仍与业务源码一致的已验证组件。

输出在本仓库忽略的 `releases/` 下：

- `yuhetang-full-update-时间戳.tar.gz`：完整总包。
- 同名 `.tar.gz.sha256`：外部校验文件。
- 同名 `.README.md`：上传之前可以直接查看的操作说明。
- 同名解压目录：可用 `python -B update.py --verify-only` 离线检查。

总包通过标准库打包，明确指定 Linux 文件权限，并重新读取压缩包逐项核验。源码、数据库副本、真实凭据、私钥、面板和网关安装器均不放入总包。已有初始化资料和照片随包交付，但不会被服务器更新脚本自动执行。

`tools/test_unified_update.py` 使用临时目录和受控的 Docker/数据库进程替身验证切换及恢复路径，不连接本机或线上数据库。它不替代真实 Linux Docker/MySQL 的部署验收。云端激活、微信客户端上传和真实消息送达仍应按总包 README 操作验证。
